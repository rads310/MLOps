## 2. Архитектура и выполненные задачи

### 2.1. Схема валидации данных (`src/schema.py` & `src/prepare.py`)
Разработаны строго специфицированные схемы валидации `Pandera` для входных сырых данных (`RawHourSchema`) и обработанного набора признаков (`FeatureSchema`):
- Проверка типов данных (целые числа, вещественные числа, строки).
- Ограничение допустимых диапазонов (например, `temp`, `atemp`, `hum`, `windspeed` in [0.0, 1.0], `hr` in [0, 23], `season` in [1, 4]).
- Контроль отсутствия пропусков (`nullable=False`) и нежелательных колонок (`strict="filter"`).

Схемы интегрированы на этапе подготовки данных (`src/prepare.py`), что гарантирует отбраковку некорректных данных до попадания в модель.

### 2.2. Сервисы предсказаний (`src/predict.py` и `src/api.py`)
1. **Пакетный инференс (`src/predict.py`)**:
   - Автоматически загружает обученную модель и выполняет предсказания для CSV-файлов или датафреймов.
   - Поддерживает предварительную валидацию через `FeatureSchema`.
2. **REST API сервис (`src/api.py`)**:
   - Реализован на базе **FastAPI** и **Pydantic**.
   - Предоставляет эндпоинты:
     - `GET /health` — проверка работоспособности сервиса и доступности загруженной модели.
     - `POST /predict` — одиночное предсказание по объекту JSON (с валидацией через `BikeRentalInput`).
     - `POST /predict/batch` — пакетное предсказание по списку объектов.

### 2.3. Модульное и интеграционное тестирование (`tests/`)
Создана система автоматических тестов (более 9 тест-кейсов), разделенная по функциональным модулям:
- `tests/test_schema.py` — проверка работы схем Pandera (прохождение валидных данных и отлов некорректных типов/диапазонов).
- `tests/test_featurize.py` — проверка корректности генерации признаков и отсутствия утечек данных (`data leakage`).
- `tests/test_predict.py` — проверка инференса модели, корректности размерностей и типов предсказанных значений.
- `tests/test_api.py` — интеграционные тесты API с использованием `TestClient` (проверка кодов ответа 200/422, формата JSON).

### 2.4. Настройка CI/CD пайплайна (`.github/workflows/ci.yml`)
В репозитории настроен автоматический workflow для GitHub Actions, который запускается при создании Pull Request и push в ветку `main`.

**Этапы пайплайна:**
1. **Setup & Linting**: Настройка Python 3.11, установка зависимостей из `requirements.txt` / `pyproject.toml`, проверка кода линтером `ruff`.
2. **Data & DVC**: Авторизация в DagsHub DVC remote через секреты (`DAGSHUB_TOKEN`), подтягивание версионированных данных (`dvc pull`).
3. **Testing**: Выполнение всех Pytest-тестов (`pytest -v`).
4. **Reproducibility**: Проверка воспроизводимости пайплайна (`dvc repro`).
5. **PR Metrics Report**: Автоматическая публикация отчёта с метриками модели (R2, MAE) в виде комментария к Pull Request.

## 4. Контрольные вопросы и ответы

### Вопрос 1. Что такое валидация данных в MLOps и чем схема Pandera отличается от статичной типизации Python?
**Ответ:**
Валидация данных в MLOps — это процесс автоматической проверки структуры, типов, диапазонов и логической целостности входных данных на всех этапах ML-пайплайна (при инжесте, предобработке и предсказании). Это необходимо для предотвращения ошибок молчаливого искажения моделей (*Garbage In, Garbage Out*).

*Отличие Pandera от статичной типизации Python (type hints / mypy):*
- **Время проверки:** Статическая типизация (type hints) проверяет типы на этапе анализа кода до его запуска и проверяет лишь типы переменных (`int`, `str`, `DataFrame`). Pandera выполняет **динамическую проверку во время выполнения (Runtime)** непосредственно над содержимым структуры `pandas.DataFrame`.
- **Глубина проверок:** Pandera позволяет задавать бизнес-правила и статистические ограничения над значениями внутри колонок (например, 0 <= temp <= 1, соответствие значению из множества категорий, проверка на null, проверка уникальности индексов и распределений), что невозможно сделать средствами статических аннотаций типов.

### Вопрос 2. Какую роль играют Unit-тесты и интеграционные тесты в ML-системах? Что такое Data Drift и Feature Drift в контексте тестирования?
**Ответ:**
- **Unit-тесты** проверяют корректность работы изолированных компонентов кода (например, что функция формирования признаков правильно вычисляет лаговые значения, что схема Pandera бракует отрицательные значения аренд).
- **Интеграционные тесты** проверяют сквозное взаимодействие модулей системы (например, отправка HTTP-запроса на FastAPI эндпоинт `/predict` -> передача данных в модель -> получение валидного JSON-ответа со статусом 200 OK).

*Понятия дрейфа:*
- **Data Drift (Дрейф данных / Covariate Shift):** Изменение статистического распределения входных признаков P(X) со временем при неизменном характере целевой переменной. *Пример:* Появление в данных за 2024 год температур в других единицах измерения (в Цельсиях вместо нормированных от 0 до 1).
- **Feature Drift / Concept Drift (Дрейф концепта):** Изменение связи между признаками и целевой переменной P(Y|X). *Пример:* Из-за внешних событий (пандемия, изменение транспортной инфраструктуры) при той же погоде и времени суток (X) люди стали арендовать принципиально иное количество велосипедов (Y).

### Вопрос 3. Зачем нужен CI/CD (Continuous Integration / Continuous Deployment) пайплайн в машинном обучении?
**Ответ:**
CI/CD в MLOps решает следующие ключевые задачи:
1. **Автоматизация контроля качества:** При каждом изменении кода или конфигураций автоматически запускаются линтеры, тесты и валидация схем, защищая ветку `main` от неработоспособного кода.
2. **Воспроизводимость пайплайн-экспериментов:** CI-сервер автоматически выполняет `dvc pull` и `dvc repro`, гарантируя, что изменения в коде не ломают полную цепочку от обработки данных до обучения модели.
3. **Предотвращение регрессии метрик:** CI позволяет автоматически сравнивать метрики (R2, MAE) новой модели с текущей производственной моделью и публиковать результаты прямо в Pull Request до принятия решения о слиянии.
4. **Быстрое развёртывание (CD):** Автоматическая сборка Docker-контейнера с FastAPI сервисом и его выкатка на продакшн-сервер при пуше в `main` или создании тега.

### Вопрос 4. Как устроен workflow в GitHub Actions, из каких основных компонентов он состоит?
**Ответ:**
Workflow в GitHub Actions описывается в YAML-файле в директории `.github/workflows/` и состоит из следующих ключевых элементов:
- **Triggers (`on`):** События, запускающие пайплайн (например, `push: branches: [main]`, `pull_request`).
- **Jobs:** Набор логических групп шагов, выполняемых на виртуальном окружении (`runs-on: ubuntu-latest`). Джобы могут выполняться параллельно или последовательно.
- **Steps:** Последовательность отдельных команд или готовых экшенов внутри одной Job.
- **Uses (Actions):** Переиспользуемые готовые блоки кода из GitHub Marketplace (например, `actions/checkout@v4`, `actions/setup-python@v5`).
- **Run:** Выполнение произвольных Bash-команд на виртуальной машине (например, `pytest`, `dvc repro`).
- **Secrets & Env:** Защищенные переменные окружения (`secrets.DAGSHUB_TOKEN`), передаваемые в виртуальную машину для авторизации в сторонних сервисах без утечки ключей в исходный код.

### Вопрос 5. В чём разница между инференсом в режиме Batch Prediction (пакетная обработка) и Real-time API (FastAPI)? В каких сценариях используется каждый из них?
**Ответ:**

| Критерий | Batch Prediction (Пакетный инференс) | Real-time API (FastAPI / REST) |
| :--- | :--- | :--- |
| **Принцип работы** | Модель периодически (по расписанию/cron) обрабатывает большие массивы данных из хранилища и сохраняет результаты в БД. | Модель обрабатывает входящий HTTP/gRPC запрос в режиме реального времени и мгновенно возвращает ответ. |
| **Задержка (Latency)** | Высокая (от минут до часов). Запуск происходит по расписанию. | Низкая (миллисекунды). Ответ требуется «здесь и сейчас». |
| **Объём данных** | Огромные объемы (миллионы строк за один запуск). | Одиночные записи или небольшие батчи от одного пользователя. |
| **Сценарии использования** | 1. Расчёт рекомендаций для пользователей на завтра.<br>2. Прогнозирование оттока клиентов раз в неделю.<br>3. Пересчёт ночных отчётов и аналитики. | 1. Оценка стоимости поездки в такси / аренды в текущую секунду.<br>2. Скоринг кредитной заявки на сайте.<br>3. Чат-боты и распознавание изображений. |
